1 Drop your own files

Causes come from two or more independent services, one file per service. Changes come from the ledger database. CSV or JSONL.

  1. User frontend: export the withdrawal requests, one row each: request id, account, amount, time.
  2. Backoffice: export the approvals, one row each: approval id, the request id it approves, account, amount (negative: money leaving), time.
  3. Ledger database: export every write to a balance: account, delta, time.
  4. Drop both causes files on Causes and the ledger file on Changes, check which service each causes file came from, and run.

The three links download the sample's files, to show the shape. A payout counts as justified only when the backoffice approval names a real request from the frontend for the same account and amount, and that request has not been paid out already. Your own column names are fine; you can map them after the first run. Already have every cause in one file with a type column? Drop that one file instead ().

    Causes, per file: id · account · asset (optional) · amount (signed) · time · ref (the id of the earlier step, e.g. the request an approval approves). type and producer come from the source you pick for the file, unless the rows carry their own.

    Changes: account · asset (optional) · delta (signed) · time · source (where the write was observed)

    Common alternatives such as request_id, approval_id, user_id, currency, created_at or approved_at are recognised. Anything else, you map after the first run.

    2 Read the result

    Sample case: a withdrawal needs a request and an approval

    Already run for you, so you can see what a finding looks like. Three exports, from three systems that do not share code or a database:

    • requests.csv from the user frontend: the user asks to withdraw.
    • approvals.csv from the backoffice: an admin approves, about an hour later, naming the request in request_id.
    • changes.csv from the ledger database: the balance writes that actually happened.

    A payout is justified only when the approval names a real request for the same account and amount, the request came from the frontend, and it has not been approved before. Five approvals:

    • A-1 approves request R-1: correct.
    • A-2 approves R-1 again: one request, two payouts.
    • A-3 approves R-404, which nobody requested: an admin paying out alone, or a replay under a new id.
    • A-4 approves 40,000 on a request for 4,000.
    • A-5 approves R-3, a "user request" that the backoffice wrote itself (service = admin-console).

    Without the request as a second source, each approval would justify itself and none of the last four would show.

    What this trial is, and isn't

    • It runs the same check as the product, on what you give it. It isn't an audit: nobody reviews the result, and nothing is signed.
    • Mapping a real export onto these two files is usually the hard part. If your export doesn't fit cleanly, that's the most useful thing to learn here.
    • A partial export produces partial findings. Some "findings" on partial data are gaps in the export, not in the ledger.
